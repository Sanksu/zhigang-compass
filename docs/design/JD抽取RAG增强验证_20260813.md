## 结论（TL;DR）

**RAG 图谱岗位参照对岗位名抽取有显著正收益：title 准确率 +19.4pp（63.9%→83.3%，3 轮稳定）；技能 F1 基本持平（-0.6pp，噪音内）。收益来自"图谱标准岗位名强约束"——LLM 对齐到图谱已有岗位而非自由发挥。**

**推荐合入**，但仅取"图谱 Position 中文岗位名"做候选约束，不注入技能列表/英文权威定义（两者均实测拖累技能 F1）。

## 关键发现

### 1. 岗位名 query 必须来自标题（非正文）
- 盲审集 `detail_raw_text` 正文可能**无岗位标题**（jd_012 正文直接是职责描述）
- 真实链路中 `JobItem.title` 可用（Scrapy 采集标题列）——**RAG 检索 query 应取标题**

### 2. 检索源取舍（对照产品 `retrieve_context` 缺口）
- **Neo4j Position 节点**（112 个中文标准岗位名）是核心增量——产品 `retrieve_context` 的岗位路只查 PG 候选池（27 条），**不含图谱 Position**
- **英文权威库定义**（occupations O*NET/LinkedIn）必须排除：jd_030 检索到 "Generative AI Engineer" 英文定义后岗位名被带偏（skills -0.278）
- **技能列表**可排除：jd_012 RAG 注入"全栈工程师（技能：Vue.js…）"后 skills -0.25（LLM 把参照技能当 JD 必备技能）；仅岗位名时 ΔF1=0

### 3. 强约束措辞 vs 弱参考
- 弱参考（"仅作参考"）→ LLM 忽略，零修正
- 强约束（"若匹配必须采用该候选名，禁止自创变体"）→ title 修正 5/12 例

## 合入建议（产品化方案）

```
JDExtractor.extract(jd_text, title_hint)
  │
  ├─ 1. query = title_hint（采集端标题）或正文首行粗提
  ├─ 2. Neo4j Position 检索（岗位名 CONTAINS 双向匹配，top 5）
  ├─ 3. prompt 注入强约束段：
  │     【图谱已知岗位候选】（强约束：若 JD 岗位与下列任一候选匹配，
  │     position_name 必须采用该候选名，禁止自创变体；仅当明显不属于
  │     任何候选时才按原规则命名）
  │     {岗位名列表，仅名字，无技能/无英文定义}
  ├─ 4. LLM 抽取（现有 TASK_TEMPLATE + 注入段）
  └─ 5. post_process（不变）
```

- Batch 场景（ETL 阶段 3）：按标题分组检索缓存，同批同岗位只查一次
- 降级：无标题/无检索命中 → 原 prompt（RAG 是增强不阻塞）
- 需同步扩展：`retrieve_context` 岗位路补 Neo4j Position（供诊断等场景复用）

## 遗留风险

1. **gold 泛化口径冲突**：盲审 gold="算法工程师"（泛），图谱标准名="大模型算法工程师"（细分）——RAG 倾向细分名，与 gold 泛化口径部分冲突；真实业务中细分更准确，需业务确认口径
2. **12 条样本量小**：title +19.4pp 稳定但样本有限；建议合入后盲审集扩到 30+ 再收尾（对齐 jd-eval-gap 记忆的 ≥0.90 目标）
3. **新岗位发现能力**：强约束可能让 LLM 倾向输出已知岗位——prompt 已含"明显不属于任何候选时按原规则"，且发现链路独立于抽取，风险可控
