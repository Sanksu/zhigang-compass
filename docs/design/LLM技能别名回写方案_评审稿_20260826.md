# 评审稿：LLM 生成技能别名 → 动态别名表（方案①，2026-08-26）

> 状态：**待算法岗张恺天确认**（待拍板项见 §8）。
> 类型：LLM 增强点之一（方案①，经"LLM 增强点评估"推荐）。非接管主链路——LLM 只做离线发现，回写后为确定性子规则，运行时不调 LLM。
> 关联：本方案借鉴 `SkillCategoryApproval`（技能分类审批闭环，#543）与 `propose_normalization`（离线批量骨架，#541）的成熟范式；复用 `skill_normalize_gate` / `known_standard_names`。

---

## 1. 目标与价值（先讲清"为什么值得做"）

用 LLM **离线批量发现"技能同义词/缩写/中英对应/版本变体"**，人工审批后回写为**动态别名表**，`normalize_skill` 运行时并查。把 LLM 结论固化成**确定性子规则**，提升技能归一/匹配/图谱质量，且运行时不调 LLM。

### 1.1 价值定位（修正后——补 SBERT 聚类盲区）

**已核实**：技能归一主路径（`normalization.py` `SkillNormalizer.normalize_many`）= **词典别名优先 + SBERT 聚合聚类**（`_agglomerative_clusters`，阈值 0.25）。**SBERT 已做语义归并**（相似技能并入同标准名）。

但 SBERT 靠**向量余弦相似度**，对以下类别的辨别力弱（**文本相似但向量不相似**），正是现有硬编码 `SKILL_ALIAS`（`dictionary_data.py`）在补、也是 LLM 命名的**独特价值**：
- **缩写/全称**：JS↔JavaScript、K8s↔Kubernetes、TS↔TypeScript
- **中英对应**：c语言↔C、vue3↔Vue.js
- **版本号**：Python3↔Python、React 18↔React
- **口语/别名**：小白↔小模型、大数据↔Big Data

**结论**：方案①不泛泛"提升归一"，而是**专补 SBERT 聚类的盲区**（非向量相似的语义等价），扩展现有硬编码 `SKILL_ALIAS` 覆盖率。这比"SBERT 已做"更精准、更可信。

### 1.2 核心设计原则
**LLM 作规则生成器，不作运行时决策器**：LLM 只在离线批量发现时调用一次（`--limit` 上限），产出 proposal 供人工审批，审批后写 `dynamic_skill_aliases`（成为确定性规则），此后 `normalize_skill` 读表、**不再调 LLM**。避免运行时非确定性 + 成本失控。

## 2. 数据流（三阶段）

```
[阶段1] 离线批量脚本 propose_skill_aliases.py --limit 40
        复用 decide_skill_normalize → merge 目标 = 候选别名对
        → gate 校验 → 落 llm_decision_records(domain=skill_normalize, status=proposal)
             ↓
[阶段2] 管理后台 approve → 落 SkillAliasProposal + sync 脚本写动态别名表
             ↓
[阶段3] normalize_skill 并查 dynamic_skill_aliases（版本化 reload，运行时不调 LLM）
```

---

## 3. 阶段1：离线批量脚本 `scripts/propose_skill_aliases.py`

- **复用** `propose_normalization.py` 骨架（`DEFAULT_LIMIT=40` / `--limit` argparse / async 核心 + `asyncio.run` sync 壳 / `_input_hash` / `persist_record`）。
- **输入池**：未归一技能名（Neo4j 无 `normalized_name` 的 Skill）+ JD 变体技能名（对齐 `name_normalization_shadow` 的候选）。
- **LLM 判定**：`decide_skill_normalize(variant, llm)` 的 `merge → target_standard` 即"别名→标准名"候选。
- **gate 校验**：`skill_normalize_gate`——merge 目标必须在 `known_standard_names()`（白名单 ∪ `_ALIAS_STANDARDS`），防 LLM 造"虚构标准名"；目标=自身判同义反复。
- **产出**：`build_record(domain=skill_normalize, entity_type="skill", entity_id=variant, structured_output={action:"merge", target_standard}, status=proposal, risk_tier=R2)`。
- **与现有 `name_normalization_propose`（阶段19）的差异**：现有已产出 merge 结论，但**没有"回写别名表"这一步**；本脚本把它收敛为"别名 proposal"，并新增审批→回写。

## 4. 阶段2：审批 + 回写（模仿 `SkillCategoryApproval` 范式）

**新模型 `SkillAliasProposal`**（`skill_alias_proposals` 表）——对齐 `SkillCategoryApproval`（`business.py:712`）：
```
id: UUID / variant: String(128) / standard_name: String(128)
/ proposal_id: String(64) / source("llm_review") / reviewed_by / review_reason / applied_to_graph(Bool)
+ UniqueConstraint("proposal_id", name="uq_skill_alias_proposal")
```
**新迁移 `20260825_003`**（down_revision=`20260825_002`）建表。

**approve 端点**（`llm_decisions.py` 加 `_approve_skill_alias`）——对齐 `_approve_skill_classify`（`llm_decisions.py:338`）：
- 校验 variant/standard_name 非空；standard ∈ `known_standard_names()`（防虚构，复用 gate）。
- 落 `SkillAliasProposal` + 决策 `approved` + `AuditLog`（operator=UUID）。
- **写动态别名表**（或由 `scripts/sync_dynamic_aliases.py` 幂等 SET——对齐"approve 写 PG、sync 写表"）。

**sync 脚本 `scripts/sync_dynamic_aliases.py`**（仿 `sync_dynamic_categories.py`）：读 `skill_alias_proposals` → 写入 `dynamic_skill_aliases` + 标 `applied_to_graph`。

## 6. 关键权衡：动态别名层 vs 整体外置

| 方案 | 说明 | 结论 |
|---|---|---|
| **动态别名层**（采用，推荐）| 新增 `dynamic_skill_aliases` 表，`normalize_skill` 并查；**不动硬编码 `SKILL_ALIAS`** | ✅ 低风险、可逐条回滚、审计清晰 |
| 整体外置 `SKILL_ALIAS` 成 yaml | 改 4 处引用（dictionary.py:17/:170/:1096-1124）+ 热加载 | ❌ 风险高（动 normalize 主路径）|
