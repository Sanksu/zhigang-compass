**责任边界**：

- ❌ 不属于本模块：LLM 结构化抽取（算法负责）、图谱入库与查询（算法负责）、匹配算法设计、图谱节点最终入库决策（算法负责）、学习路径生成逻辑（算法负责）。


**预期成果（M2 阶段）**：

1. 国内爬虫：3 平台（A 级 BOSS/智联 + C 级 脉脉）（Scrapy + Playwright + 单 IP 直连 + 300+ UA + 8-15s 随机间隔 + 指数退避；脉脉走 S2+S3 合规链路：学术豁免声明 + 脱敏 + 限频 ≤ 100 req/h + 夜间运行 23:00-06:00）。
2. 国际爬虫：4 平台（A 级 LinkedIn API/Monster + B 级 Indeed/Glassdoor，走网络代理 Rule 模式：国内直连 + 国际代理池）。
3. 清洗管线：长度过滤 → 核心词检测 → 四维评分 → SimHash 64-bit 汉明距离 ≤ 3 + MinHash 128 permutation 兜底 → 时效加权 `weight = exp(-0.01 × (days_ago - 30))`。
4. 时滞/通胀检测：M2 仅搭框架（M3 图谱基线后补齐 SAI 计算）。
5. 课程平台：M2 仅设计 Schema（M3 对接 3 平台：中国大学MOOC/Coursera/edX）。
6. **★ 黄金集**：≥ 50 条高质量 JD 标注（U3 LLM 预标注 + 人工校验 ≥ 20%，M3 中段补齐至 ≥ 100 条，同时阻塞算法评测与测试，须优先交付）。
7. Airflow DAG（crawl → clean → dedup → validate_temporal → detect_inflation → structure → load_to_db → index_neo4j）失败重试 2 次 + 告警通知（webhook + 邮件）。

**验收指标**：

- 单日采集 ≥ 100 条 JD（国内 ≥ 60 + 国际 ≥ 40，P0）；P1 目标 ≥ 200 条/日。
- SimHash 去重准确率 ≥ 95%，每条数据含五标（publish_time/crawl_time/decay_weight/source_platform/region）。
- 时滞/通胀检测：M2 仅框架，M3 调优至召回率 ≥ 80%。
- 黄金集 ≥ 50 条（M2 末），M3 中段补齐至 ≥ 100 条（题目硬性要求）。
- 国际源占比 ≥ 30%。
- 题目硬性要求：黄金集 ≥ 100 条、JD 解析 ≥ 90%、简历提取 ≥ 90%、人岗匹配 ≥ 90%。

## 第三部分：代码管理规范

### 3.1 技术岗规范

#### 3.1.1 分支策略

采用 `main` + `develop` + `feature/*` 三层模型：

| 分支 | 命名规则 | 用途 | 保护规则 |
|------|---------|------|---------|
| `main` | 固定 | 生产就绪代码，仅通过 PR 合入 | 禁止直推，需 ≥ 1 人审查 + CI 通过 |
| `develop` | 固定 | 集成分支，日常开发基线 | 禁止直推，需 ≥ 1 人审查 |
| `feature/<模块>-<简述>` | `feature/fe-resume-match` | 新功能开发 | 从 `develop` 切出，完成后合回 `develop` |
| `fix/<模块>-<简述>` | `fix/be-jwt-refresh` | Bug 修复 | 从 `develop` 切出 |
| `hotfix/<简述>` | `hotfix/crash-on-3d` | 生产紧急修复 | 从 `main` 切出，合回 `main` 与 `develop` |

**模块前缀对照**：`fe`（前端）/ `be`（后端）/ `algo`（算法）/ `data`（数据）/ `test`（测试）/ `docs`（文档）。

#### 3.1.2 提交信息格式

采用 Conventional Commits 规范：

```
<type>(<scope>): <subject>

<body 可选>

<footer 可选，如 Closes #123>
```

**type 取值**：

| type | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(fe): 实现图谱四种视图切换` |
| `fix` | Bug 修复 | `fix(be): 修复 JWT 刷新 401 死循环` |
| `docs` | 文档变更 | `docs: 完善第 5 章知识图谱本体` |
| `style` | 代码格式（不影响逻辑） | `style(fe): 统一缩进为 2 空格` |
| `refactor` | 重构 | `refactor(algo): 抽取 LLM 调用为独立模块` |
| `perf` | 性能优化 | `perf(fe): 图谱 Sprite 替代几何体` |
| `test` | 测试相关 | `test: 新增 TC-KG-03 用例` |
| `chore` | 构建/工具变更 | `chore: 升级 Vite 至 6.0` |
| `ci` | CI 配置 | `ci: 添加 GitHub Actions 测试流水线` |

**subject 要求**：≤ 50 字符，祈使句（"实现"而非"实现了"），首字母不大写，结尾不加句号。

```python
# backend/data/pipeline/dedup.py
from simhash import Simhash

def hamming_distance(a: Simhash, b: Simhash) -> int:
    return a.distance(b)

def is_duplicate(text_a: str, text_b: str, threshold: int = 3) -> bool:
    """汉明距离 ≤ 3 视为重复"""
    return hamming_distance(Simhash(text_a), Simhash(text_b)) <= threshold
```

```yaml
    runs-on: ubuntu-latest
```

### 5.3 代码集成流程

#### 5.3.1 集成测试环境

- **开发环境**：本地 `docker compose up -d`（每人独立）。
- **集成分支环境**：`develop` 分支自动部署到共享测试服务器（M3 起由后端岗配置）。

#### 5.3.2 冲突解决方法

1. **预防**：每日开工先 `git pull --rebase`。
2. **冲突处理**：
   - 同模块冲突：开发者自行 rebase 解决。
   - 跨模块冲突（如接口签名）：项目群 @相关人协商。
   - `backend/openapi/` 目录冲突：必须后端 + 前端双人确认。
3. **回滚**：`git revert <commit>` 优先于 `git reset`（保留历史）。

#### 5.3.3 集成测试顺序

```
单元测试通过 → 契约测试通过（前后端接口一致）
→ 集成测试通过（API + 数据库）
→ E2E 测试通过（全流程）
→ 性能压测达标
→ 合并到 develop
```
