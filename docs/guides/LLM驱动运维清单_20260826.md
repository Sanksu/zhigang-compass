## 五、审批→落图操作序（人工通道）

1. 每日 ETL 自动产 proposal（开关全开时）→ `/admin/llm-decisions` 决策页
2. admin 批准（须填 review_reason，operator 必须是 users.id UUID）
3. 落图执行器（**先 --dry-run 再实跑**）：
   - 关系：`scripts/sync_dynamic_relations.py --dry-run`
   - 归一（rename/merge 图变异）：`scripts/sync_dynamic_normalization.py --dry-run`
   - 分类：`scripts/sync_dynamic_categories.py`
   - **技能别名（#559）：无需 sync——approve 即写 skill_aliases 并自动 reload，normalize_skill 立即可并查**

## 六、脚本运行环境红线

- **propose/sync 系列脚本目标环境是 Linux 容器**。Windows 本机直接跑会踩 `asyncio.run` × asyncpg 跨事件循环（`Future attached to a different loop`）——`sync_dynamic_normalization` 已在 #559 改单事件循环修复；其余 propose 脚本在 Windows 仍可能触发，**统一在容器/226 内跑**。
- 历史教训：同一 sync 函数内多次 `asyncio.run` 各开新 loop，asyncpg 连接池跨 loop 静默失败（症状：`applied_to_graph` 不标记）。新增脚本一律单 `asyncio.run` 包全程。

## 七、226 部署专项（实测踩坑）

1. **必须带 images override**：`docker compose up -d -f docker-compose.yml -f docker-compose.images.yml`——漏带则 worker 落到 base 默认死代理 `host.docker.internal:7890`，无外网。
2. **worker 容器 TZ**：compose 已补 `TZ=Asia/Shanghai`（否则 arq cron 按 UTC 触发，ETL 永不点火）。
3. `runtime_settings.json` 是 bind-mount 持久化——重建容器不丢，但**改完须重启 worker 生效**。
4. LLM 配置同步到 226 后须重启 api+worker（provider 链启动时构造）。

## 八、监控要点

- `llm_decision_records` 按 domain×status 汇总：`GET /admin/llm-decisions/summary`（proposal 积压=待审队列长度）。
- LLM provider 健康检查：`check_llm_providers_health`（全 False 先查 api_key 是否为空，再查网关连通）。
- 技能别名生效验证：`normalize_skill("<variant>")` 返回 standard 即并查生效（skill_aliases approved 行 + reload 后）。
