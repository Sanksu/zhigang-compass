## 四、高危发现(5)

### H1 [安全·数据越权] ✅ 简历解析缓存全局共享,PUT 编辑把人工修正写入共享行
- **位置**:`backend/app/api/v1/resume.py:146-168`(缓存命中补建归属)、`:305`(编辑合并)
- **机制**:ResumeCache 按 file_hash 全局唯一(L151 注释声明有意设计)。用户 B 上传与 A 相同字节的文件 → 命中 A 的缓存行并获得 ResumeFile 归属;此后任一方调用 `PUT /resume/{id}`,`_merge_fields` 把人工修正直接写入这条唯一 parsed_data —— **A 修正的字段内容对 B 可见**(get_resume 返回完整 parsed_data)。人工修正是用户生成内容而非文件派生物,超出了"同文件共享解析结果"的设计边界。
- **后果**:跨用户信息泄露(触发条件:同字节文件 + 任一方使用过编辑功能)。
- **建议方向**:编辑时 copy-on-write(为编辑者克隆独立 parsed_data 行)或 parsed_data 按 user 维度分叉;属安全类,修复 PR 须人工逐行审查。

### H2 [安全·生产姿态] ✅ 生产 fail-fast 仅两项,debug 默认 True 使 SQL echo 泄 PII
- **位置**:`backend/app/main.py:45-49`(仅校验 secret_key/admin_password)、`app/core/config.py:20`(`debug: bool = True`)、`:48`(`cors_origins=["*"]`)、`app/core/database.py:14`(`echo=settings.debug`)
- **机制**:`APP_ENV=production` 但漏配 DEBUG 时,asyncpg 将把含绑定参数的 SQL 全量打进日志——简历 PII、密码哈希列尽在其中;CORS 全开亦无拦截。neo4j_password 弱默认同样漏网。
- **附带**:AGENTS.md §6.2 写的是"强校验 SECRET_KEY 长度",实现实为"等于默认值即拒启",文档与实现口径不一(轻微)。
- **建议方向**:production 校验清单补 `debug=False 强制`、`cors_origins≠["*"]`;一行成本。

### H3 [前端·数据完整性] ✅ 图谱节点详情的需求%/市场趋势为哈希编造
- **位置**:`frontend/src/routes/graph-page.tsx:322-329`(hash → demand 0.5~1.0 / trend −0.1~0.7)、`components/graph/node-detail-panel.tsx:365-383`(渲染为"需求 X%""趋势↑")
- **机制**:契约(openapi.yaml)中 demand/trend 仅存在于 GapSkill/LearningPathItem 与演化趋势端点;图谱五个钻取端点均无此字段。用户看到"市场需求 63%、趋势 ↑42%"实为技能名哈希。
- **对照**:dashboard-page.tsx:59 已明确"无后端来源的指标不展示",此处理念不一致;该问题自 08-14"前端假数据"中危演变残留至今。
- **建议方向**:删除编造或显式标注"暂无数据"(演示叙事风险:评委追问数据来源即穿帮)。

### H4 [前端·正确性] ✅ 匹配页无条件重算 ROI 覆盖后端值,evidence 重建丢弃后端溯源
- **位置**:`frontend/src/routes/resume-match-page.tsx:216`(`roi = (demand*(trend+1))/GAP_COST` 无 `??` 回退,**恒覆盖**)、`:218-227`(evidence 本地重建,toGapItem L100 透传的后端 MatchEvidenceItem 被丢弃)、`:235-242`(以本地 roi 重选 Top3,可推翻后端 high_roi 标记)
- **对照**:后端 `services/learning_path/gap.py:140-184` 对每条 gap 恒定填充 demand/trend/roi/evidence 并打 high_roi ◇;两端公式不同(后端 cost=base_hours×熟练度缺口,前端 GAP_COST 常量),同一技能必得两个不同 ROI。
- **性质**:L95/L123 注释声称"透传/兜底",实际是无条件覆盖——#341 后装字段后端已全量返回,这套前端逻辑应删而非留。
- **连带**:demand/trend 的 `?? hashNum(...)` 兜底仅 Redis 快照跨部署 <24h 残留时可短暂生效,属死代码;且两处编造区间还不一致(graph 页 −0.1~0.7 vs 此页 −0.5~1)。

### H5 [算法·仅参考→移交张恺天] ✅ 幻觉防控第二道防线只算不拦,"unverified 不入图"门控不存在
- **位置**:`backend/app/workers/etl_tasks.py:807`(结果写回 `snapshot["cross_validation"]` 后**全仓无读取方**,grep 证实)、`app/services/kg/aggregation.py:348`(source_count 仅记录,无置信度/源数门槛拦截入图)
- **机制**:`CONFIDENCE_GRAPH_MIN = 0.6` 定义于 cross_validate.py 内部但无人消费;"单源标 unverified 不入生产图谱"(设计文档 §6.3 第二道防线、赛题自检报告引用的宣传点)在代码中无对应拦截路径。单源 JD 技能照常聚合入图,且 #338 单源兜底(jd_count≤2 时 must_count>0 即 must)进一步让单源数据可判 must。
- **影响**:对外宣称的三道防线中第二道现状是审计数据面而非拦截面;若评委核查代码链路,宣传与实现不符。
- **移交**:是否补门控、还是改宣传口径,须算法岗张恺天亲自裁决(AGENTS.md §4.1 算法红线)。

## 五、中危发现(8)

### M1 [测试] ✅ integration 测试未打 marker,`-m "not integration"` 排除失效(有本机失败实证)
- `tests/integration/test_graph_integration.py`、`test_domain_match_integration.py` 全文无 `pytestmark = pytest.mark.integration`(grep 证实);实际排除靠 conftest 端口探测——CI 无基础设施"碰巧不跑",本机 docker 在跑时普通 `pytest` 会拉起集成测试。**本轮实测即发生**:1524 passed 中混入了集成用例,且 `test_cloud_candidate_hits_more`(L82-89,断言依赖真实图谱数据形态)已因数据演化失败。库内另有 12 处"admin 登录失败则 skip"类条件跳过,存在长期静默 0 覆盖却绿灯的风险。
- **建议**:两个文件补 marker(各一行)+ 把数据耦合断言改为对数据形态的前置断言或移出默认集。

### M2 [安全] ✅ XFF 首条目可信 + Redis 故障 fail-open,限流可被绕过
- `core/middleware.py:67-75` 生产取 XFF **第一个**合法 IP(离客户端最近、客户端可控),限流键 `rate:{ip}:{module}` 可轮换伪造头无限重置——登录爆破/注册洪水/LLM 10/min 限制全部失效;`:84-85` ip 为空直接放行;`:99-101` Redis 异常 fail-open。代码注释自认"仍无法防 IP 伪造,限流为增强能力"(设计接受的残余风险,故定中危):当前单实例部署前面只有本地 relay,XFF 由 relay 追加,真实暴露有限;若未来置于不可信代理后需改信任跳数策略。

### M3 [可用性] ✅ jti 黑名单 fail-closed:Redis 故障 = 全站认证瘫痪
- `api/deps.py:41/65` 黑名单检查裸调 redis.get 无 try:Redis 挂时所有认证请求(含 get_optional_user 的公开图谱端点)500;Redis 重启丢键后已注销 token 复活至自然过期(access ≤30min)。与 M2 叠加:Redis 是限流(fail-open)、黑名单(fail-closed)、熔断状态(fail-open)三种语义的单点,故障时行为不一致且无告警。建议:get_redis 层统一降级策略 + 告警接线(ALERT_WEBHOOK_URL 已预留一行即启)。

### M4 [安全卫生] ✅ E2E 规格硬编码疑似真实管理员口令
- `frontend/e2e/full-flow.spec.ts:11`、`graph-mode.spec.ts:11`、`mocks/api.ts:124`:`password: 'mm2877417'`。非占位符形态(DEPLOY.md 要求非弱口令),疑似某环境真实 ADMIN_PASSWORD 入库。建议:**立即轮换该口令**,spec 改环境变量注入(CI secrets/本地 .env)。

### M5 [审计] ✅ admin accounts 域四端点零审计写入
- `api/v1/admin_routes/accounts.py:22-115` 用户列表/创建/改角色/物理删除全程不写 AuditLog(audit 域存在但仅 position_reviews 在写)。提权、禁用、GDPR 删除等最敏感操作不可追溯,与系统自身审计设计相悖。补 4 条 AuditLog 即可。

### M6 [前端门禁] ✅ vitest 覆盖率阈值从未在任何地方执行
- `vite.config.ts:40` thresholds 80/80/70/80(仅核心子集)只在带 `--coverage` 时生效;`package.json:11` test 脚本与 `ci-frontend.yml:49` 均不带 coverage → 门禁纸面化;tests/README 宣称"后端 ≥70%,前端核心 ≥95%"无一处配置落地。建议 CI 加一步 `vitest run --coverage`(或删阈值避免误导)。

### M7 [E2E 双轨] ◇ 有状态 mock fixture 缺契约 required 字段
- `frontend/e2e/mocks/api.ts:50`(RESUME_LIST item 仅 {id},契约 required 含 file_name/skills/total_years)、`:52-55`(EVOLUTION_VERSIONS 缺 node_added 等 4 个 required 字段)。登录态机/401 降级/refresh cookie 模拟与真实行为对齐良好,但列表 fixture 是"最小渲染集",双轨漂移方向为 mock 落后于契约——后端收紧校验时 mock 不报警。建议 fixture 对齐 required 字段。

### M8 [可观测性] ✅ 启动预热零痕迹吞错
- `main.py:103-104` `_prewarm_semantic` 整体 `except Exception: pass`,连 logger 都没有(docstring 声明"失败静默"是有意设计,语义不可用时自动降级纯规则)。但 SBERT 加载失败的唯一症状是线上匹配莫名变弱,排障无线索。加一行 `logger.warning(...)` 保住降级语义的同时恢复可观测。其余 97 处 except 经抽检均为有日志/有注释的降级,判定可接受(详见 §七正面对照)。
