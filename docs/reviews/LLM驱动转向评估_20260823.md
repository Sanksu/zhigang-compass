# LLM 驱动转向评估（2026-08-23）

## 结论

当前项目**不适合直接切换为“LLM 唯一驱动”**；适合继续演进为“LLM 负责语义判断/候选生成，确定性规则、词典、图算法和人工门控负责生产一致性”的混合架构。LLM 基础设施和部分业务链路已可运行，但岗位/技能归一、分类、治理尚未形成全面、可审计、可回放的 LLM 闭环。

## 已具备

- 统一 OpenAI-compatible provider 链、priority/enabled 配置、Pydantic/instructor 结构化输出、同步 10s 与异步 30s provider fallback、429 退避、5xx 熔断：`backend/app/services/extraction/llm_provider.py:1-15,295-531`。
- JD 抽取已是 LLM 主路径，失败降级规则抽取；批量抽取有按条数/文本长度分组、错位防护和逐条降级：`backend/app/services/extraction/jd_extractor.py:38-90,92-169`；ETL 使用 batch_size=8、timeout=180、max_batch_chars=8000、concurrency=6：`backend/app/workers/etl_tasks.py:639-777`。
- 技能后处理已有别名、白名单、后缀清洗、噪音/软技能过滤和灰名单注册：`backend/app/services/extraction/dictionary.py:61-89,1084-1115,1162-1258`；统一入口为 `canonical_skill_name`：`backend/app/services/extraction/post_processor.py:83-113`。
- 技能离线归一采用“词典优先 + SBERT 层次聚类”，写回前有巨型簇、映射率门禁：`backend/app/services/extraction/normalization.py:1-15,95-160,163-243`；ETL 异常时拒绝写回并告警：`backend/app/workers/etl_tasks.py:867-915`。
- 技能簇在规则无法判定时调用 LLM，失败回退规则标签：`backend/app/services/graph_algorithms/postprocess.py:208-318`、`backend/app/services/graph_algorithms/cluster_llm.py:79-118`。
- 字典守卫已覆盖技能、岗位、课程候选；先规则筛选，再 LLM 裁决，硬门禁、自动/人工分级和审计提案已落地：`backend/app/services/extraction/dict_guard.py:114-182,185-330`、`backend/app/workers/dict_guard.py:97-242`。
- 岗位国家职业分类对齐仍是规则精确命中 + SBERT 兜底，不是 LLM 主路径：`backend/app/services/kg/occupation_align.py:1-15,142-210`。

## 不能直接“全 LLM 化”的关键事实

1. **岗位归一仍高度规则驱动。** `normalize_position_name` 依赖数百条岗位关键词族、英文映射、停用词、白名单、技能路由和人工维护别名；通用兜底岗位无技能/未命中时直接丢弃：`backend/app/services/extraction/dictionary.py:209-401,434-688,690-826,975-1070`。岗位名 LLM 审查方案仍是设计稿/灰度方案，尚未成为生产闭环。
2. **技能分类不是 LLM 分类。** `skill_category` 直接从 `backend/configs/skill_whitelist.yaml` 的 605 个条目和 23 个类别读取，白名单外统一为“未分类”：`backend/app/services/extraction/dictionary.py:61-89`。LLM 输出的 category 没有成为最终分类事实源，后处理仍以词典/规则保护为准。
3. **技能关系治理仍是静态字典。** 先修、父子、替代关系从 `configs/skill_prerequisites.yaml`、`configs/skill_relations.yaml` 同步，未由 LLM 生成并经过关系级证据验证：`backend/app/services/kg/skill_relations.py:1-12,49-112`。
4. **生产约束决定不能让 LLM 独占裁决。** 项目设计明确要求 Schema 校验、白名单/证据门控、单源实体不入生产图、失败规则降级和人工审核：`docs/design/设计文档.md:663-671,742-805`。这不是临时实现细节，而是幻觉防控和可追溯性要求。
5. **治理闭环仍非完全 LLM 原生。** dict-guard 的候选来自规则/引用数/相似度初筛，LLM 只评估候选；自动生效仅限低影响、高置信的收紧/删除类动作，放行类动作必须人工审批：`backend/app/services/extraction/dict_guard.py:163-182`。
6. **运维与评测尚不足以支撑全面切换。** 已有 provider fallback 和单测，但缺统一的 model/prompt/schema 版本、token/cost/latency、重试/降级率、在线回归门禁和按 provider 对照矩阵；设计声明的全部失败延迟队列/DLQ闭环也未在 provider 层真实实现。配置 key 为 YAML 明文落盘（虽 gitignore），缺密钥管理/轮换/并发写审计。
7. **重爬不重抽造成语义滞后。** 正文更新不会自动触发抽取，需人工重抽或 rebuild：`docs/design/设计文档.md:550`。

## 量化门槛

- 技能归一写回覆盖率 100%、映射率 5%~90%、最大簇 ≤ max(50, 技能总数×2%)：`docs/design/执行计划.md:112-118`。设计记录的 6593 技能样本映射率 57.2%、最大簇 AI=106/上限132，说明当前 SBERT+门禁路线可控，但不能据此证明 LLM 分类已达标。
- 设计验收要求 JD/简历/匹配准确率 ≥90%、实体 F1≥.88、证据覆盖 100%、新岗位召回≥80%且误报≤15%：`docs/design/设计文档.md:131-138,219-235`。岗位 LLM 审查方案另要求分类≥90%、修正≥80%、误杀 0，并默认先关闭灰度，未形成生产验收实现。
- 运行时约束：同步 LLM 10s、异步每 provider 30s/总 90s、普通/LLM 限流 100/10 req/min：`AGENTS.md:6.4`、`docs/design/设计文档.md:760-805`、`docs/design/设计文档.md:146-161`。

## 推荐路线

### P0：先补可控性，再扩大 LLM 范围

- 建立统一 `LLMInvocation` 记录：任务/entity、provider/model、prompt/schema 版本、耗时、token/cost、重试、最终结果、降级原因、证据 ID。
- 实现真实 ARQ retry budget、延迟队列/DLQ、幂等键和总墙钟时限；区分超时、429、5xx、校验失败，避免全部映射成“超时”。
- 配置 API 使用 Pydantic 请求模型；密钥改为 secret manager/加密存储并支持轮换、审计、并发写保护；确认 admin RBAC。
- 保留现有确定性门禁作为生产写入边界，LLM 只能输出候选/裁决，不直接绕过白名单、证据和人工审批。

### P1：岗位/技能 LLM 语义层灰度化

- 落地岗位名审查器：输入岗位标题、JD 技能、来源和历史聚合证据，输出标准岗位、分类、置信度、理由、证据；默认只生成 proposal，不自动改生产。
- LLM 分类仅对“白名单外、灰名单、跨类别/低频/冲突”候选启用；白名单内走确定性快速路径。
- 为岗位归一、技能归一、分类、关系、治理分别建立 golden set 和 provider×model×prompt/schema 回归矩阵；通过分类≥90%、修正≥80%、误杀=0及现有归一三门禁后逐步放量。
- 让 LLM 提议反哺 alias/whitelist/relations，但所有落盘变更保留版本、证据、审批人和回滚记录。

### P2：扩大到语义增强而不是替代全部确定性路径

- 对职业分类对齐、技能父子/替代/先修关系增加 LLM 语义候选，但以 O*NET/职业分类、JD 共现、课程证据和人工审核做多源验证。
- 建立可回放的提示词/schema/model 版本和成本配额；对低价值重复 JD 使用缓存/批处理，对高风险岗位和新技能保留人工队列。
- 只有在连续多个窗口满足质量、成本、延迟、误杀和回滚指标后，才考虑将某一子域从“规则主导”提升为“LLM 主导”，不建议一次性全域替换。

## 最终判定

- **技术可行性：有条件可行。** 现有 provider、结构化输出、降级、审计和评测基础足以承载 LLM 增强。
- **当前直接切换：No-Go。** 岗位归一/分类/治理的事实源仍是规则、白名单、SBERT 和人工门控；关键 LLM 运维、可观测、回滚和岗位审查门禁尚不完整。
- **推荐目标：LLM-centered、deterministic-guarded。** 让 LLM 负责开放世界语义理解和候选提议，让规则/词典/图算法负责可重复性，让证据与人工审批负责生产写入。这样既能扩大新岗位/新技能覆盖，又不牺牲图谱稳定性、可解释性和答辩验收口径。
