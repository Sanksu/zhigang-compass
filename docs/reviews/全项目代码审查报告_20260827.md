## 一、P0（2 条）——方案①别名回写「双断链」，已交付功能 100% 静默失效

**P0-1 动态别名回写在所有进程永不生效，approve 返回假成功**
`app/services/extraction/dictionary.py:1213` 模块级 `_DYNAMIC_ALIAS_LOWER = {}` 初始为空；`:1238` `reload_dynamic_aliases()` 内部 `asyncio.run(_load())`——唯一调用方 `_approve_skill_alias`（`llm_decisions.py:452-455`）是 async 端点，事件循环运行中调 `asyncio.run()` 必抛 `RuntimeError`，被 `dictionary.py:1240` `except Exception` 静默吞掉返回旧缓存；且 `main.py` lifespan 与全部 worker 启动路径**无任何加载钩子**（全仓 grep 仅此一处调用）。后果：管理员批准别名 → 接口返回 `effects_applied=True`、注释宣称「approve 后立即可并查」，但 `normalize_skill:1102` 的「词典→动态→白名单」三层中动态层在 API/worker 任何进程恒为空——**方案①（#559，D1-D6 拍板落地）名存实亡**。测试以 `asyncio.run(_approve_skill_alias(...))` 直调并 monkeypatch 掉 reload（`tests/admin/test_skill_alias_approval.py:72`），恰好掩盖死链。修复：reload 提供 async 版本供端点 await + main.py/worker on_startup 启动加载 +（见 P1-5）跨进程刷新机制。〔实证：主审逐行复核三方证据链〕

**P0-2 skill-aliases 列表契约包装漂移——前端 `apiGet` 取 `res.data.data` 得 undefined，动态别名表页运行时断**
实现 `app/api/v1/admin_routes/skill_aliases.py:65-68` 返回裸 `{items,total,limit,offset}`（未过 `ok()` 包装）；契约 `openapi.yaml:1637-1674` 声明 `{code,msg,data:{items,…},trace_id}` 包装；前端 `frontend/src/lib/api.ts:187-190` `apiGet` 严格返回 `res.data.data`，`admin-skill-aliases-page.tsx:55` 按契约类型取 `data.items` → 实际拿到 `undefined`。中间件只碰 header 不做全局包装（`middleware.py:121-143` 逐项核实），排除假阳性。修复：实现侧补 `ok(...)` 包装对齐契约（前端零改动）。〔实证：契约/实现/apiGet 三方核对〕

## 二、P1（6 条）

**P1-1 JD 证据并发共用同一 AsyncSession——生产环境 jd_evidence 大面积静默为空**
`app/workers/matching.py:152` `asyncio.gather(*(_one(n) for n in names))`，每个 `_one` 在**同一个** session 上 `await session.scalars(...)`（`jd_rerank.py:113` 直用传入 session）。SQLAlchemy 2.0 AsyncSession 明确禁止并发协程使用：除首个外均抛 `InvalidRequestError`，被 `_one` 的 `except Exception` 吞掉降级空行 → 阶段 B 匹配推荐附带的 JD 级证据多数岗位静默缺失。测试只覆盖纯函数未覆盖此编排路径。修复：每岗位独立 session（`async_session_factory()`）或改顺序查询。〔实证〕

**P1-2 阶段 20/21 propose 编排在事件循环内同步调 LLM——开启灰度开关即冻结 ARQ worker**
`propose_normalization.py:176/227/286`、`propose_relations.py:131` 在 async 编排中直接调用 `decide_position_name/decide_skill_normalize/decide_skill_relation`（底层 `extract_structured` 为同步 def，`llm_provider.py:431`），单条最坏 30s×3 provider 链期间 worker 事件循环完全阻塞（健康检查 cron、并发任务全部停摆）。同域阶段 19 `name_normalization_shadow.py:132/171` 已正确用 `asyncio.to_thread`——复制时遗漏。`skill_category_review.py:81` 也已正确。修复：统一 to_thread（一行级×4 处）。〔实证〕

**P1-3 match_recommend PG 镜像失败未回滚——PendingRollbackError 逃逸，任务状态卡 running**
`workers/matching.py:359-372`：内层 `except` 吞 flush 异常后继续赋值，`:372` 的 commit 在外层 try 之外——session 已处 pending-rollback 态时 commit 必抛 `PendingRollbackError`，ARQ 任务异常终止，task.status 无法落终态。修复：except 内 `await session.rollback()`。〔疑似·高置信，建议补一条失败路径测试〕

**P1-4 裸 dict 请求体蔓延至 12 处，文本字段无 max_length（上轮 P2 未修且新代码延续）**
`position_reviews.py:111/271/387`、`llm_decisions.py:157/462`、`accounts.py:59/91`、`position_edit.py:267`、`dict_guard.py:158`、`crawl.py:202`、`config.py:283` 均 `req: dict` 手工校验；reason/keyword/username 无长度上限，超长文本靠 DB 列兜底或 500，违背「LLM 输出 Pydantic 强校验」同源的防线精神（auth/match/etl 已示范正确做法）。另 operator UUID 守卫不一致：`llm_decisions.py:146-151`/`dict_guard.py:191-194` 校验而 `position_reviews`/`position_edit`/`config` 不校验，sub 缺失 fallback `"admin"` 撞 `AuditLog.user_id` UUID 列即 500。〔实证〕

**P1-5 别名链路两处结构性缺口（P0-1 修复后的下一环）**
① 跨进程失效：即使修好 reload，API 进程内存刷新到不了 ARQ worker（ETL 抽取链 `normalize_skill` 主消费方，`etl_tasks.py:1091`），无轮询/版本号/TTL 机制；② 候选源断供：`propose()` 只编排 position/skill 两域（`propose_normalization.py:351-362`），别名回写仅有手动脚本 `scripts/propose_skill_aliases.py`，ETL 阶段 20 不产出别名候选——「动态别名表」将无新增来源。〔实证〕

**P1-6 测试两洼地原样未动（上轮点名→本轮复核仍在）**
`workers/matching.py` 覆盖率 **10%**（166 语句 150 未覆盖：`resume_parse`/`_match_jd_candidates`/`match_recommend` 编排全零测试——恰是 P0-2/P1-1/P1-3 三条缺陷所在层）；`services/kg/skill_relations.py` **27%**（九类关系落 Neo4j 写入路径无回归网，答辩图谱路径）。同洼地：`propose_normalization.py` 21%、`propose_relations.py` 20%、`workers/diagnosis.py` 15%。修复方向：对齐 dict_guard 测试模式（mock 外设跑真实编排，含失败路径）。〔实证〕
