## 一、P1 发现（7 条）

**P1-1 dict-guard 动态过滤文件未跨容器共享——自治闭环在标准部署下端到端断链**
`docker-compose.yml:91-93/164-166` 只挂载 `llm_providers.yaml` 与 `runtime_settings.json`；`dynamic_filters.py:29` 写 `configs/skill_filters_dynamic.json` 落容器私有层。后果：worker 每日 LLM 评估产生的 auto 拦截，api 容器（kg/matching/resume 均经 `is_noise_skill`）永远看不见；管理端 approve 也到不了 ETL worker。方案 §4「同 runtime_settings 模式」未落实。修复成本一行（bind mount）或改 DB 单源。〔dict-guard 深审〕

**P1-2 桑基图计数未过滤 REQUIRES——技能-技能边混入「岗位」列**
`api/v1/evolution.py:519-523` `freq = Counter(e.get("source") for e in edges if e.get("target")==skill_id)` 无 relation 过滤；快照全量导出含 `BELONGS_TO/ALTERNATIVE_OF/PREREQUISITE_OF/EVOLVED_FROM` 技能→技能边，上游技能会以「岗位」身份进入桑基图，与 docstring/前端文案「REQUIRES 频次」不符。答辩演示路径上的业务正确性缺陷。测试夹具只造 REQUIRES 边故未暴露。同根问题见算法条目 A-1、P2 freq_ratio。〔演化深审〕

**P1-3 evolution 快照全量加载扩散至 4 端点，无 in-flight 防击穿、signals/trends 无缓存**
`evolution.py:321` `_load_snapshots` 被 4 端点调用，`:162`（/signals）、`:483`（/trends）另行全量加载且无缓存；skill_flow 缓存键含 id×top 细粒度放大 miss。量级：每期 ~20k 节点+60k 边 ≈ 20-30MB，90 期满额单次 miss ~2GB + PG 传输 ~450MB，看板一次并发 4-5 个端点 = 4-5 份全量副本。当前 ~40 期勉强可容忍，是 08-15「演化看板 30s 超时/TTL 风暴」教训在新模块的回归（graph.py:44 已有 in-flight 表未沿用）。〔性能专项〕

**P1-4 dict_guard 影响面模拟逐候选全表 LIKE**
`workers/dict_guard.py:260` `JDRaw.raw_text.contains(term)` 无时间窗无索引，每批 ≤40 候选逐条执行；10 万行×3KB 每扫 ~300MB，40 次 ≈ 12GB IO。建议限 7 天窗口（#399 已传 tz-aware datetime，可直接加 created_at 过滤）或 pg_trgm 索引。〔性能专项〕

**P1-5 grounding.py 六处宽 except 全静默，零日志零计数**
`grounding.py:224/265/334/349/398/508`，全文件 `grep -c logging` = 0：语义路/Neo4j 全文/Redis/LLM 失败一律无声降级——语义检索可在生产静默瘫痪数周不被发现。同批 etl.py 自己修了「无声吞错」（#378 L-9 聚合告警），风格自相矛盾。至少 logger.warning + 降级计数。〔幻觉防控深审〕

**P1-6 compute_confidence 无下界钳制，可产负值触发 ValidationError（已复现）**
`confidence.py:154` `final = min(base+bonus+delta, 1.0)` 缺 `max(…,0)`：jd/source/growth 全 0 + graph_grounding=0.0 → final=−0.075，被 `schemas.py:70 Field(ge=0.0)` 拒绝。当前默认权重不触发，但 #388 让 w_evidence 运行时可调（0.4 即可达），孤立新技能+低频样本即崩 discovery worker。一行修复。〔幻觉防控深审，实证〕

**P1-7 thresholds.py 坏值直接炸管线，违背「缺失不阻断」承诺（已复现）**
`thresholds.py:54-59` `_get` 的 try 只包 `data.get`，`int()/float()` 转换裸奔：配置单键写 null → TypeError 传播，SimHash/时滞检测全停。#388 主场景就是管理员运行时改此文件——改错一个值 = 质量门禁全停摆，恰与该 PR 目标相悖。转换包 try 回退默认。〔幻觉防控深审，实证〕

## 三、算法条目——Z-score 占比口径归一化（分支 `300fa33`，交张恺天裁决）

**结论**：方向正确——占比口径消除采集总量乘性噪声，等比例波动场景测试实证有效；但分母边集不对称 + 混合口径无防护，可复活批量伪告警。

| # | 级别 | 意见 |
|---|---|---|
| A-1 | 必须确认 | 分子/分母边集不对称（`trend_service.py:34-39`）：分母仅 REQUIRES、分子计所有 `sk_` target 边（含 BELONGS_TO 等）→ 比值可 >1。`state_machine.py:96-100` 已有 REQUIRES 过滤先例。与 P1-2 桑基问题同根——evolution 模块需统一 REQUIRES 过滤约定 |
| A-2 | 必须确认 | 混合口径序列无防护（`detector.py:120,138`）：fallback 逐窗口独立，旧快照（无 relation 字段）取值 ~60、新快照 ~0.06 → z 全失真，批量伪 declining 复活——恰是本提交要消灭的场景。应整序列同口径：任一窗口缺分母则全序列退回计数 |
| A-3 | 必须确认 | 反向伪信号未处理：部分采集源故障 → 总量腰斩但某技能计数不降 → 占比翻倍 → 伪 emerging。建议消费 `GraphVersion.data_warning`（evidence 萎缩 <50% 检测已存在），总量骤变窗口抑制判定或降置信 |
| A-4 | 建议 | 设计文档 §7.1（:834 仍写 30 天窗口频次）与 CHANGELOG 均未同步——SSOT 断链，答辩叙事缺口 |
| A-5 | 建议 | `EvolutionSignal.historical_mean/std` 语义从计数变占比，schemas/openapi 描述未注；mom_growth 仍计数口径，同一对象双口径并存 |
| A-6 | 可接受 | 阈值 2.0/±1.5 在总量恒定时数值等价（尺度不变性），MIN_FREQ=10 小基数保护有效 |

测试三缺口：混合口径序列、部分源故障反向场景、分子含非 REQUIRES 边（现有夹具恰好全 REQUIRES，测试通过不能证明口径正确）。另注意：discovery 对「缺 relation」默认计入、evolution 默认排除，两模块同概念约定相反。
